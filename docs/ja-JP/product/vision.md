# 製品のビジョンと範囲

GreenERは「どのアプリケーションを監視しているか」「消費量を裏付ける証拠は何か」「推定エネルギーと排出量をどう解釈するか」に答えます。検出、メトリクス、地域情報、履歴を統合し、調査と優先順位付けを支援します。

## 対象者

| 対象者 | 必要なこと |
| --- | --- |
| インフラ管理者 | アプリケーションと環境の変化を把握する。 |
| 運用・環境分析担当 | 期間を調査し、比較可能な結果と欠損を理解する。 |
| 開発・評価チーム | 環境を再現し、受け入れ基準を実証する。 |

ダッシュボードと環境参照は公開。`/login`でメール/パスワード、または有効化済みGoogleを使用。AdminはGoogle後も6桁TOTPの設定/確認が必要。Analyst/Visitorに管理権限は付与しません。UIセッションはメモリ内で、再読み込み後は再ログイン。backendはJWT、セッション、現在の役割と状態を確認し、認証不正は401、権限不足は403。新規ルートは既定で保護します。

## 範囲と提供状況

基準：`origin/develop`、コミット`c343698`、2026年11月8日確認。環境の版は異なる場合があり、マージは公開完了を証明しません。

| 機能 | 文書化された状況 |
| --- | --- |
| 一覧、検索、フィルター、ページ送り、画面遷移、12言語 | UIに実装済み。 |
| 検出、ライフサイクルイベント、定期収集、インシデント、永続化 | バックエンドに実装済み。 |
| 運用状態、元データのメトリクス、収集証拠と方法論 | APIと詳細画面で提供。専用画面では記録済みのモデル、式、パラメーター、係数を再計算せずに説明します。失敗・欠損・古いデータは区別されます。 |
| 環境分析、時系列、アプリ別の寄与調査 | APIで提供され、アプリ詳細画面に統合済み。 |

## 利用の流れと価値

1. アプリケーションを検索して詳細を開き、ID、所在地、状態を確認する。
2. 最後の試行、最後の有効な観測、データ不在を区別して変化を調べる。
3. 詳細画面で期間と粒度を選び、系列とカバー率を読み、欠損をゼロにせずbucketの寄与を確認する。

[利用ガイド](../guide/monitoring)は既存機能、[エピック](../roadmap)は期待する機能を説明します。

## 制約と評価

推定値は直接の電力計測でも、操作による削減効果の因果的な証明でもありません。トランザクション当たりの効率には処理量データが必要です。詳細の時系列では、1つのアプリと同じ長さの直前期間を比較できます。アプリ間比較やダッシュボードでの期間比較は含みません。CSV出力と列設定はFigmaに存在するだけではMVPに含まれません。地図は任意です。

レビューでは、アプリを見つけられるか、ゼロと欠損を区別できるか、期間・単位・証拠まで追跡できるかを確認します。困難、フィードバック、変更は[#133](https://github.com/Seliganessecodigo/ABP-3DSM/issues/133)と[#134](https://github.com/Seliganessecodigo/ABP-3DSM/issues/134)へ記録します。所要時間、満足度、性能の数値目標には基準値と承認が必要です。

## 利用ガイド

`/history`でアプリを選び、`applicationId`、期間、粒度をURLに保持。保存系列、フィルター、表示タイムゾーン、イベント、番号付きページ、bucket検査を提供。寄与も5・10・15・20件または全件のページ切替に対応。backendのbucketはUTCで、表示タイムゾーンでは再集計しません。詳細の重ね合わせは同じアプリの直前同期間と比較します。

`/administration/calculations`でアプリと日付を選び原本とプレビューを比較。終了日はUTCの一日全体を含み、APIは`[from,to)`。公開操作で現行モデルと過去地域の現在係数を使用し、保存しません。上限30日・10,000観測。応答は`original`、`preview`、`warnings`、`status`（`available`、`empty`、`partial`）。係数障害でも算出可能なエネルギーを保持。百分率は同じ単位・カバー率と正の基準値が必要です。

`/methodology`にエネルギー、排出量、カバー率、分析の4タブと例示データ。ログインした各役割は自分のタブだけ保存し、楽観的リビジョン競合は409。表示しきい値は全体設定・計算・外部通知を変更しません。保存した期間/粒度は詳細URLで未指定の場合のみ適用。記録済み方法論は`/services/:id/methodology`と選択時の`collectionId`で保持します。

同じ組織のAdminは`expectedStatus`と理由を指定し`ACTIVE`、`BLOCKED`、`DEACTIVATED`を変更可能。ブロック/無効化で全セッションを失効、再有効化後は新規ログイン。自分自身と最後の有効Adminを保護。期待状態の不一致は409、目標状態到達済みは冪等成功。共通監査は成功を変更と同じトランザクション、拒否をロールバック外で記録し、実行主体を明記、秘密を除外。役割管理全体やパスワード復旧はこのAPIの範囲外です。
